# Impact Analysis Gateway

> **強制等級**：任何修改、無例外。
> 每一個對帶 ID 產出物的修改（無論大小）皆必須自主執行本協議。

---

## 觸發條件

本協議在以下任一情況發生時**強制自主執行**：

1. 新增任何帶 ID 的產出物
2. 修改任何帶 ID 的產出物（內容、描述、連結）
3. 刪除任何帶 ID 的產出物
4. 修改任何追溯連結
5. 修改任何已通過 HITL 閘門的產出物
6. 修改任何 Stage 的審查維度或工具配置

---

## 執行協議

```
┌─────────────────────────────────────────────────────────┐
│  IMPACT ANALYSIS GATEWAY（每次修改自動執行）             │
│                                                         │
│  Step 1: 識別變更                                       │
│  → 記錄變更的 ID 和變更內容                             │
│  → 分類：新增 / 修改 / 刪除                             │
│  → 記錄變更時間戳和觸發 Stage                           │
│                                                         │
│  Step 2: 正向影響追溯                                   │
│  → 從變更 ID 沿正向追溯鏈走訪所有下游 ID                │
│  → 標記每個下游 ID 為「可能受影響」                     │
│  → 遞迴展開至追溯鏈末端                                │
│                                                         │
│  Step 3: 反向影響追溯                                   │
│  → 從變更 ID 沿反向追溯鏈走訪所有上游 ID                │
│  → 檢查上游 ID 的語意是否仍與變更後內容一致             │
│  → 標記不一致的上游 ID                                  │
│                                                         │
│  Step 3.5: 全方向連結追溯（FR-022）                     │
│  → 除縱向主鏈外，追溯所有方向的連結：                  │
│    - ADR → FR/NFR (justifies)：                         │
│      ADR 的 rationale 是否仍然成立？                    │
│      ADR 的 decision 是否與變更矛盾？                   │
│      若不成立 → 標記 SUPERSEDED → 需新 ADR             │
│    - FEA → NFR (constrains)：                           │
│      NFR 的約束是否仍被滿足？                           │
│      若違反 → 嚴重度自動升至 MAJOR                     │
│    - RISK → FEA (mitigates)：                           │
│      風險緩解措施是否因變更失效？                       │
│    - EVT → CLS (emitted-by)：                           │
│      事件來源是否因變更而斷裂？                         │
│    - INV → CLS/ALG (formalizes)：                       │
│      不變量是否因變更而被破壞？                         │
│    - LESSON → skill (guards)：                          │
│      已有的左移守衛是否因變更而失效？                   │
│  → 對每個受影響 ID：讀取其完整文件驗證語意一致         │
│  → 標記所有方向的受影響 ID                             │
│                                                         │
│  Step 4: 爆炸半徑計算                                   │
│  → blast_radius = count(affected_downstream)            │
│                   + count(inconsistent_upstream)          │
│                   + count(affected_lateral)  ← 新增      │
│  → 跨 Stage 影響 = 受影響 ID 橫跨幾個 Stage            │
│                                                         │
│  Step 5: 嚴重度分類                                     │
│  ┌──────────────────────────────────────────┐            │
│  │ COSMETIC (blast_radius = 0)             │            │
│  │ → 僅格式/拼寫修正，無語意變更           │            │
│  │ → 動作：記錄至 ADR 變更紀錄，繼續      │            │
│  ├──────────────────────────────────────────┤            │
│  │ MINOR (blast_radius = 1-3, 同 Stage)    │            │
│  │ → 動作：自主更新受影響 ID               │            │
│  │ → 重新執行微驗證迴圈                    │            │
│  │ → 記錄至 ADR 變更紀錄                   │            │
│  ├──────────────────────────────────────────┤            │
│  │ MODERATE (blast_radius = 4-10           │            │
│  │          或跨 1 個 Stage)               │            │
│  │ → 動作：自主更新受影響 ID               │            │
│  │ → 重新驗證受影響 Stage 的出口閘門       │            │
│  │ → 記錄至 ADR 變更紀錄                          │            │
│  ├──────────────────────────────────────────┤            │
│  │ MAJOR (blast_radius > 10                │            │
│  │       或跨 2+ Stage)                    │            │
│  │                                         │            │
│  │ Step M1: 全貌映射（AI 自主）            │            │
│  │ → 透過追溯矩陣沿正向/反向鏈展開        │            │
│  │ → 列出所有受影響 ID 及其 Stage          │            │
│  │ → 定義每個受影響 ID 的預期驗證方式      │            │
│  │ → 產出完整影響報告                      │            │
│  │                                         │            │
│  │ Step M2: 自主全面修正（AI 自主）        │            │
│  │ → 按影響報告逐一更新所有受影響 ID       │            │
│  │ → 每個修正後執行微驗證迴圈              │            │
│  │ → 遞迴傳播至追溯鏈末端                  │            │
│  │                                         │            │
│  │ Step M3: 預定義驗證 + 缺口識別          │            │
│  │ → 按 Step M1 定義的驗證方式逐一檢驗     │            │
│  │ → 重新驗證所有受影響 Stage 出口閘門     │            │
│  │ → 識別預定義驗證方式的不足處            │            │
│  │ → 若有不足：補充驗證並重新檢驗          │            │
│  │                                         │            │
│  │ Step M4: HITL 確認（人類驗證完成品）    │            │
│  │ → 呈現：影響報告 + 修正清單 + 驗證結果  │            │
│  │ → 人類確認修正完整性和正確性             │            │
│  │ → 記錄至 ADR 變更紀錄                          │            │
│  └──────────────────────────────────────────┘            │
│                                                         │
│  Step 6: 產出影響分析紀錄                               │
│  → 寫入對應 ADR 的「變更紀錄」區段                       │
│  → 更新追溯矩陣                                        │
└─────────────────────────────────────────────────────────┘
```

## 影響分析紀錄格式

> 影響分析紀錄直接寫入對應 ADR 的「變更紀錄 (Implementation Records)」區段。
> 格式見 `docs/adr/ADR-TEMPLATE.md` 的「變更紀錄」區段。

```markdown
### 變更 #N: [變更摘要]

**觸發時間**: [ISO 8601]
**觸發 Stage**: Stage [N]
**變更類型**: 新增 / 修改 / 刪除
**變更 ID**: [變更的 ID]
**變更內容**: [變更前] → [變更後]

**影響分析**:
- 爆炸半徑: [N] 個 ID
- 跨 Stage 影響: [N] 個 Stage
- 嚴重度: COSMETIC / MINOR / MODERATE / MAJOR

**受影響 ID**:
| ID | Stage | 影響類型 | 處理狀態 |
|----|-------|---------|---------|
| FR-003 | Stage 3 | 語意需更新 | ✅ 已修復 |

**閘門重新驗證**:
- [ ] Stage 3 出口閘門：✅ 重新通過

**處理狀態**: ✅ 完成
```

## 工具整合

| 情境 | 工具 | 用法 |
|------|------|------|
| 程式碼變更影響 | `/understand-diff` | 分析 diff 的元件影響和爆炸半徑 |
| 文件變更影響 | 手動追溯 | 沿追溯鏈標記受影響 ID |
| 跨 Stage 影響 | `/review` | 程式碼審查跨 Stage 一致性 |
| 自主修復驗證 | 微驗證迴圈 | 執行 TRACEABILITY.md 的微動作驗證 |

---

## 禁止行為

1. **禁止跳過影響分析**：無論修改多小，皆必須執行
2. **禁止僅更新變更 ID 而不更新下游**：必須遞迴傳播
3. **禁止在 MAJOR 影響下跳過全貌映射**：必須先完成 Step M1-M3，再呈報 HITL 確認
4. **禁止在未完成影響分析前進入下一個微動作**
