# ADR Governance Framework

> **治理層**：跨切面強制執行
> 所有決策（人類 prompt 決策 + AI 自主決策）皆須以 ADR 形式記錄。
> ADR 為決策的單一事實來源；CHANGE-MANAGEMENT、IMPACT-ANALYSIS、TECH-DEBT 為 ADR 的關聯產出物。

---

## 核心原則

1. **每個決策都是 ADR**：無論來自人類 HITL 輸入或 AI 自主判斷，凡影響架構、流程、範圍、安全的決策皆記錄
2. **分層分類**：ADR 依性質分為 6 個類別，各有專屬範本
3. **雙向追溯**：每個 ADR 連結至觸發它的上游 ID 和受它影響的下游 ID
4. **關聯治理產出物**：變更紀錄直接寫入對應 ADR、技術債（DEBT-xxx）、風險（RISK-xxx）皆追溯至授權它的 ADR
5. **高內聚低耦合**：每個 ADR 精確捕捉一個 Decision Unit，不多不少（見下方定義）
6. **資訊新穎性門檻**：僅記錄無法從既有知識推導的資訊，但寧多勿漏（見下方定義）

## ADR 粒度決策框架：Decision Unit 理論

> 類比 SOLID 的 SRP（Single Responsibility Principle）：一個模組應只有一個變更理由。
> 對 ADR 的對應：**一個 ADR 應只有一個存在理由** — 它精確捕捉一個 Decision Unit。

### Decision Unit 形式化定義

**Decision Unit (DU)** 是滿足以下三個性質的最小決策集合：

| 性質 | 定義 | 違反時的後果 |
|------|------|-------------|
| **共享關注點 (Shared Concern)** | 集合中所有選擇都在回答同一個架構問題 | 若不共享 → 多個不相關決策混入同一 ADR → 未來修改一個決策時被迫閱讀不相關內容 |
| **後果耦合 (Consequence Coupling)** | 任一選擇的後果分析依賴於集合中其他選擇 | 若後果獨立 → 成本效益分析可獨立進行 → 應拆為獨立 ADR 以保持分析清晰 |
| **反轉原子性 (Reversal Atomicity)** | 集合中的選擇必須一起反轉；單獨反轉任一會導致系統狀態不一致 | 若可獨立反轉 → 未來工程師應能只反轉其一而不觸碰其他 → 必須分為獨立 ADR |

**為什麼是這三個性質？**

- **共享關注點**直接對應 SRP：不同問題 = 不同變更理由 = 不同 ADR
- **後果耦合**確保 ADR 內的成本效益分析是自洽的：若後果獨立，合併分析只會模糊個別決策的取捨
- **反轉原子性**確保 ADR 服務於未來決策者：ADR 存在的核心目的是支援未來的「要不要反轉這個決策」判斷。若兩個選擇可獨立反轉，它們必須是獨立 ADR

### 三個形式化測試

#### 測試 1：決策邊界測試 (Decision Boundary Test, DBT)

```
1. 用一句話陳述 ADR 的核心決策
2. 對 ADR 中的每個元素（背景細節、理由論點、後果項）提問：
   「移除此元素是否會損害對這個一句話決策的理解？」
3. 內聚分數 = 必要元素數 / 總元素數
4. 判定：
   ≥ 0.8 → 高內聚 ✅
   < 0.8 → 低內聚 → 拆分 ADR
```

**為什麼 0.8？** 留 20% 空間給必要的上下文鋪陳（背景、約束），這些元素不直接支撐決策但提供理解所需的框架。低於 0.8 表示超過 1/5 的內容與核心決策無關，應獨立成另一個 ADR。

#### 測試 2：後果封閉測試 (Consequence Containment Test, CCT)

```
1. 列出 ADR 中所有後果（正面 + 負面 + 風險）
2. 對每個後果追溯：它是否源自核心決策？
3. 判定：
   所有後果皆源自同一決策 → 高內聚 ✅
   存在後果源自不同決策 → 多個 DU 被混入 → 拆分
```

**為什麼需要 CCT？** DBT 檢查輸入端（背景和理由），CCT 檢查輸出端（後果）。一個 ADR 可能在輸入端看起來內聚，但後果卻暴露了隱藏的多重決策。

#### 測試 3：反轉獨立測試 (Reversal Independence Test, RIT)

```
1. 識別 ADR 中的所有子決策
2. 對任意兩個子決策 A 和 B 提問：
   「能否反轉 A 同時保持 B 不變，且系統不產生架構矛盾？」
3. 判定：
   任一對可獨立反轉 → 它們是獨立 DU → 拆為獨立 ADR
   所有對皆不可獨立反轉 → 原子 DU → 同一 ADR ✅
```

**為什麼 RIT 是最關鍵的測試？** ADR 的終極用途是支援未來決策者判斷「要不要反轉」。RIT 直接測試這個用途：若兩個選擇的反轉是獨立的，強行合併只會讓未來反轉操作的爆炸半徑不必要地擴大。

### 內聚 vs 耦合：正交維度

| 維度 | 定義 | 量測方式 | 優化方向 |
|------|------|---------|---------|
| **內聚 (Cohesion)** | ADR 內部元素的相關程度 | 移除任一元素對 ADR 完整性的損害程度 | 最大化：每個元素都不可或缺 |
| **耦合 (Coupling)** | ADR 之間的依賴程度 | 修改 ADR-A 時必須連帶修改的其他 ADR 數量 | 最小化：修改一個不影響其他 |

**關鍵洞察：高內聚自然降低耦合。** 當每個 ADR 精確捕捉一個 DU 時，修改一個決策只影響真正依賴它的 ADR，而非因為被綁在一起的不相關決策。

**四象限分析：**

```
            高內聚
              │
  理想 ✅     │     可接受
  獨立且聚焦   │     聚焦但有依賴鏈
              │
低耦合 ───────┼──────── 高耦合
              │
  問題         │     最差 ❌
  雜亂但獨立   │     義大利麵決策
              │
            低內聚
```

### ADR-GATE 頻率的具體判定

ADR-GATE 頻率不是「每輪一個」或「每 Stage 一個」，而是**每個 Decision Unit 一個**：

| 迭代情境 | DU 判定 | ADR 行為 |
|---------|---------|---------|
| 用戶選 [1] 繼續迭代，反饋是精煉同一問題 | 同一 DU（共享關注點、後果耦合） | 追加至現有 ADR-GATE 的迭代紀錄 |
| 用戶選 [2] 加入新需求，且新需求改變問題空間 | 新 DU（不同關注點） | 產出新 ADR-GATE |
| 用戶選 [2] 加入新需求，但新需求是原問題的延伸 | 同一 DU（RIT 不通過：不可獨立反轉） | 追加至現有 ADR-GATE |
| 用戶選 [3] 通過 | 關閉現有 DU | 將現有 ADR-GATE 狀態改為 Accepted |
| 不動點偵測建議終止 | 視用戶回應 | — |

**判定流程：**

```
用戶在 HITL 閘門輸入新內容 I
  │
  ├─ I 回答的是與當前 ADR 相同的架構問題？
  │   ├─ 是 → RIT：反轉 I 是否必然要反轉當前 ADR？
  │   │       ├─ 是 → 同一 DU → 追加至現有 ADR
  │   │       └─ 否 → 新 DU → 產出新 ADR
  │   └─ 否 → 新 DU → 產出新 ADR
  │
  └─ I 是 [3] 通過 → 關閉現有 ADR → Accepted
```

## 資訊新穎性評估框架（Information Novelty Assessment）

> 適用於 Phase 1 探索性問答、以及任何產出「發現」而非「決策」的活動。
> 核心立場：**寧可多記錄（偽陽性），不可漏記錄（偽陰性）。**

### 為什麼偏向偽陽性？

- **偽陽性的成本**（記錄了可推導的資訊）：O(1) — 多一條記錄，邊際儲存和閱讀成本
- **偽陰性的成本**（漏記了不可推導的資訊）：O(n) — 知識遺失，未來 n 個決策可能因缺乏此資訊而次優
- 不對稱性明確：偽陰性的系統性傷害遠大於偽陽性

### 可推導性梯度（Derivability Gradient）

| 等級 | 定義 | 判定 | 範例 |
|------|------|------|------|
| L0: 明示 | I 逐字存在於現有文件中 | 不記錄 | 「FR-001 是使用者認證」（已寫在 requirements.md） |
| L1: 平凡推論 | I 可從單一文件經一步顯然推論得出 | 不記錄 | 「A 依賴 B 且 B 依賴 C → A 傳遞依賴 C」 |
| **L2: 多步推論** | **I 需讀 2+ 文件且經 2+ 推論步驟** | **記錄** | 「結合 Stage 3 的架構圖和 Stage 5 的類別圖，發現模組 X 和 Y 有隱性循環依賴」 |
| **L3: 跨域綜合** | **I 需結合不同領域知識** | **記錄** | 「這個效能特性其實有安全隱患：快取加速暴露了時序攻擊面」 |
| **L4: 隱性/默會** | **I 揭示未被文字化的設計意圖或歷史脈絡** | **記錄** | 「這段程式碼之所以用這個奇怪的 pattern，是因為當時 framework 的 bug」 |
| **L5: 湧現** | **I 描述單一元件文件無法預測的系統行為** | **記錄** | 「三個獨立正確的模組組合後產生死鎖」 |

### 為什麼門檻設在 L2？

- L0-L1 推導是**確定性的**：任何具備基本邏輯能力的讀者**必然**會得出相同結論
- L2+ 推導是**機率性的**：讀者**可能**得出結論，取決於專業度、注意力、時間
- 機率性推導意味著知識**有遺失風險**，因此必須記錄以消除風險

### 形式化判定：「新工程師」啟發法

```
給定一位具備領域能力的工程師，已完整閱讀所有現有文件一遍：
  │
  ├─ 此人能在 15 分鐘內確定推導出 I？
  │   ├─ 確定能 → L0/L1 → 不記錄
  │   ├─ 不確定 → L2+ → 記錄
  │   └─ 確定不能 → L3+ → 必須記錄
  │
  └─ 有疑慮時 → 記錄（偽陽性偏好）
```

**為什麼是「15 分鐘」？** 這是一個合理的注意力窗口。超過 15 分鐘的推導鏈意味著知識已經散落到需要主動搜尋和拼湊的程度，記錄它可以為未來讀者節省這個搜尋成本。

### Phase 1 記錄決策樹

```
/understand-chat 或 /understand-explain 產出資訊 I
  │
  ├─ Step 1: I 是否逐字存在於現有文件？ → 是 → 不記錄
  ├─ Step 2: I 是否為現有內容的平凡改寫？ → 是 → 不記錄
  ├─ Step 3: I 能否從單一文件經單步推論得出？ → 是 → 不記錄
  ├─ Step 4: I 是否需要 2+ 文件 或 2+ 推論步驟？ → 是 → 記錄
  ├─ Step 5: I 是否揭示隱性設計意圖或默會知識？ → 是 → 記錄
  ├─ Step 6: I 是否描述湧現行為？ → 是 → 記錄
  └─ Step 7: 仍有疑慮？ → 記錄（偽陽性偏好）
```

記錄目標位置：`docs/exploration-log.md`（非 ADR，因為是「發現」而非「決策」）。
當發現觸發了設計決策時，才從 exploration-log 升級為 ADR。

## ADR 類別層次結構

| 類別 | 前綴 | 定義 | 決策者 | 範例 |
|------|------|------|--------|------|
| **STRUCTURAL** | `ADR-STR-xxx` | 系統架構、模組邊界、技術棧選擇 | AI 提案 + HITL 核准 | 三層分離架構、資料庫選型 |
| **GOVERNANCE** | `ADR-GOV-xxx` | 流程規則、閘門標準、審計要求 | AI 提案 + HITL 核准 | 微驗證步數變更、SonarCloud 門檻 |
| **SECURITY** | `ADR-SEC-xxx` | 安全控制決策、威脅模型回應 | AI 提案 + HITL 核准 | 加密演算法選擇、認證機制 |
| **SCOPE** | `ADR-SCP-xxx` | 功能邊界、MVP 定義、排除理由 | 人類決策（Red Team 回應） | 功能納入/排除、CEO Review 模式 |
| **GATE** | `ADR-GATE-xxx` | HITL 閘門決策紀錄 | 人類決策 | Stage 3 通過、加入新需求 |
| **OPERATIONAL** | `ADR-OPS-xxx` | 部署、監控、事件回應 | AI 提案 + HITL 核准 | CI/CD 策略、Canary 門檻 |

### 編號規則

```
ADR-{CATEGORY}-{NNN}
例：ADR-STR-001（結構類）
    ADR-GOV-001（治理類）
    ADR-GOV-002（治理類）
    ADR-SEC-001（安全類）
    ADR-SCP-001（範圍類）
    ADR-GATE-S3-001（Stage 3 閘門決策第 1 次）
    ADR-OPS-001（營運類）
```

## ADR 與治理產出物的整合關係

```
ADR-{CAT}-xxx（決策記錄）
  │
  ├── 觸發 → ADR 變更紀錄（見 ADR-TEMPLATE.md 變更紀錄區段）
  │          └── blast_radius, 受影響 ID, 閘門重驗證
  │
  ├── 產生 → DEBT-xxx（技術債項目，見 TECH-DEBT.md）
  │          └── RICE 分數, 四象限分類, 修復計畫
  │
  ├── 紀錄 → ADR 變更紀錄（見 ADR-TEMPLATE.md 變更紀錄區段）
  │          └── 變更類型, 根因分類, 左移動作
  │
  └── 緩解 → RISK-xxx（風險項目）
             └── 影響 × 機率, 緩解策略
```

### 整合規則

1. **每個變更必須追溯至一個 ADR**：變更紀錄直接寫入對應 ADR 的「變更紀錄」區段
2. **每個 DEBT-xxx 可追溯至 ADR**：技術債的 `產生原因 ADR` 欄位記錄導致該債務的決策
3. **MAJOR 影響分析結果 → 產出新 ADR**：記錄人類的處理決策
4. **所有變更類型 → LESSON-xxx 追溯至 ADR**：根因左移的教訓連結至原始決策（CREATE/MODIFY/FIX 皆適用，無例外）

## ADR 生命週期

```
Proposed → Accepted → Superseded
              │
              └→ Deprecated
              └→ Amended (minor update, 不產生新 ADR)
```

| 狀態 | 定義 | 轉移條件 |
|------|------|---------|
| Proposed | AI 提案，等待 HITL 核准 | 自動產生 |
| Accepted | 人類核准，生效中 | HITL 確認 ✅ |
| Superseded | 被新 ADR 取代 | 新 ADR Accepted 且聲明取代 |
| Deprecated | 不再適用但保留歷史 | HITL 決策 |
| Amended | 小幅修正，不改變核心決策 | AI 自主 + 影響分析 COSMETIC/MINOR |
